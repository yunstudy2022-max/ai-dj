### 🗺️ claudio.fm 系統架構樹狀圖

這個架構分為四大區塊，將「運算大腦」與「視覺舞台」解耦，確保未來搬上雲端時能無縫接軌。

```text
claudio.fm 系統架構 (Local -> Cloud)
│
├── 1. 外部輸入與輸出 (I/O)
│   ├── Input: YouTube Live Chat (觀眾留言)
│   └── Output: YouTube Live Stream (影音推流)
│
├── 2. 視覺舞台與推流 (Frontend - Windows/雲端桌面)
│   ├── React UI (OBS Browser Source)
│   │   ├── Wabi-sabi 視覺組件 (底片顆粒、黑膠旋轉)
│   │   ├── 打字機組件 (DJ 口白即時顯示)
│   │   └── WebSocket Client (聆聽後端狀態更新)
│   ├── OBS Studio
│   │   ├── 畫面擷取 (React UI)
│   │   └── 音訊擷取 (指定擷取虛擬音軌)
│   └── Virtual Audio Cable (VAC) -> 確保系統通知聲不入鏡
│
├── 3. 核心控制器 / Agent 大腦 (Backend - WSL Ubuntu)
│   ├── 主迴圈 (Main Event Loop) -> 控制 15 分鐘/首的節奏
│   ├── 記憶與過濾層 (Memory & Moderation)
│   │   ├── 本地字典檔 (擋髒話/敏感詞)
│   │   └── 常客記憶庫 (SQLite/JSON，紀錄聽眾 ID 與偏好)
│   ├── 人設調度器 (Persona Manager)
│   │   └── 依據時間自動切換 (晚安下班/深夜吧檯/I人時光)
│   ├── 佇列管理器 (Queue Manager) -> 解決音樂生成的延遲
│   │   └── 音檔下載、緩存、定時清理 (Garbage Collection)
│   └── WebSocket Server -> 發送畫面更新指令給 React UI
│
└── 4. 外部大腦與樂器 (External APIs)
    ├── OpenAI Moderation API (免費二級留言審查)
    ├── Claude 3.5 Sonnet / GPT-4o API (情緒分析 + 寫歌 Prompt)
    ├── ElevenLabs API (高品質 DJ 語音合成)
    └── Suno / Udio API (生成無人聲純樂器音樂)

```

### 📋 開發工作清單 (Work Breakdown Structure)

這份清單以「模組化」為原則，建議你一個區塊測試完畢後，再串接下一個。

#### Phase 1: 環境與基礎設施架設 (Infrastructure)

* [ ] **後端環境：** 在本地 Windows 安裝 WSL Ubuntu，建立 Python 虛擬環境（`venv` 或 `conda`）。
* [ ] **依賴套件安裝：** 安裝 `websockets`, `aiohttp` (非同步 API 呼叫), `pygame` 或 `vlc` (Python 播放音檔用)。
* [ ] **音訊路由設定：** 安裝 Virtual Audio Cable。將 Python 的音訊輸出指向 Line 1 (Virtual Cable)，並在 OBS 中只擷取 Line 1。
* [ ] **OBS 基礎設定：** 建立 1080p 畫布，準備好推流金鑰。

#### Phase 2: 前端視覺與通訊 (Frontend & UI)

* [ ] **React 專案初始化：** 將你現有的 HTML/CSS 刻板轉為正式的 React 專案（Vite 是一個好選擇）。
* [ ] **建立 WebSocket Client：** 讓前端能連線到 Python 後端。
* [ ] **設計狀態接收邏輯：** 當後端傳來 `{ "action": "update_speech", "text": "..." }` 時，觸發打字機動畫。
* [ ] **設計音樂狀態邏輯：** 接收後端指令來控制黑膠唱片的 `paused` / `live` CSS 狀態。
* [ ] **OBS 測試：** 將本地運行網址（如 `localhost:5173`）加入 OBS 的瀏覽器來源，確認底片雜訊與濾鏡不掉幀。

#### Phase 3: 後端大腦與邏輯實作 (Backend Controller)

* [ ] **開發 YouTube 留言爬蟲：** 實作定時抓取（Polling）最新留言的函數（建議使用 `pychat` 庫或直接打 YouTube Data API）。
* [ ] **實作雙層過濾器：** 建立 `bad_words.json` 進行正則表達式阻擋，並寫好串接 OpenAI Moderation API 的函數。
* [ ] **時段排程器：** 寫一個函數判斷當前系統時間，回傳對應的 System Prompt（例如 01:00 回傳「I人時光」的人設設定檔）。
* [ ] **主控迴圈 (The Loop)：** 這是最核心的腳本。撰寫 Async 非同步函數，讓「抓留言 ➡️ 呼叫大腦 ➡️ 呼叫語音/音樂 ➡️ 推送前端」能按順序執行不卡死。
* [ ] **音檔播放與管理模組：** 撰寫腳本自動將下載的 MP3 放入特定資料夾，播放完畢後移動到 `/archive`，並定時刪除 3 天前的舊檔案避免硬碟爆滿。

#### Phase 4: 外部 API 串接與測試 (API Integrations)

* [ ] **LLM API 串接：** 將過濾後的留言送給大語言模型，要求強制回傳 JSON（包含 `analysis`, `dj_speech`, `music_prompt`）。
* [ ] **TTS API 串接：** 將 `dj_speech` 送給 ElevenLabs，測試語音下載與生成速度。
* [ ] **Music API 串接：** 測試 Suno 或 Udio 的 API。這是最容易超時的一環，必須寫好 **Retry（重試）** 與 **Timeout（超時）** 的防呆機制。如果生成失敗，要能 fallback（退回）播放本地端的備用 Lo-Fi 庫。

#### Phase 5: 上線前壓力測試與雲端搬遷 (Testing & Deployment)

* [ ] **本地 2 小時壓測：** 建立私人 YouTube 直播，開啟腳本讓它自己跑 2 小時，觀察記憶體是否外洩（Memory Leak）、音頻是否與畫面脫軌。
* [ ] **環境變數打包：** 將所有 API Keys 寫入 `.env` 檔，確保程式碼可移植。
* [ ] **雲端部署：** 租用雲端電腦（如我們先前討論的 12核/1050Ti/32G 方案）。
* [ ] **雲端無頭測試 (Headless Check)：** 在雲端主機啟動系統與 OBS 後，關閉遠端桌面連線（RDP），用另一台電腦看直播，確認畫面與聲音沒有因為失去顯示器焦點而中斷。

### 💡 開發環境與 API 最佳實踐建議

#### 1. 環境建議 (IDE & OS)

* **編輯器：** 強烈建議使用 **Cursor**。它在處理這類 API 串接與非同步 (Async) 程式碼時，能幫你省下大量查閱官方文件的時間。
* **開發 OS：** 在本地開發時，開一個 **WSL 2 (Ubuntu)** 環境來跑 Python 後端。這會讓你在處理音檔下載、路徑管理和排程任務時，比在 Windows 原生環境少踩很多坑；前端 UI 則維持在 Windows 端的 Node.js 跑即可。

#### 2. API 選擇建議與避坑指南

* **🧠 LLM (大腦)：Claude 3.5 Sonnet**
* **原因：** Claude 在文字風格的模仿（Tone of Voice）上遠勝 GPT-4o。它能更精準地抓到你想要的 Wabi-sabi 與內斂感，不會出現太多 AI 味的陳腔濫調（像是「讓我們一起探索...」）。


* **👄 TTS (語音)：ElevenLabs**
* **原因：** 目前市場上情緒表達最自然的語音 API。
* **建議：** 不要用預設聲音。花點時間在他們的 Voice Library 挑選一個「低沉、帶點氣音、咬字不會太用力的亞洲或美式口音」，這會是 claudio.fm 的靈魂。


* **🎸 Music (樂器)：Suno API**
* **原因：** 生成速度相對穩定，且支援極度詳細的 Prompting。
* **坑點警告：** 非官方的 API wrapper 很多，建議選擇有穩定維護的開源庫。務必在 Prompt 裡加上 `Instrumental`, `No vocals`, `No voices`，不然 AI 有時會自己加上奇怪的人聲哼唱。



這個清單的優先級很明確。建議你這個週末可以先從 **Phase 3 的「抓取留言 + Claude 生成 JSON」** 寫一個簡單的 Python 腳本來試試水溫，看看 AI 回傳的 `dj_speech` 有沒有達到你心中的那個標準？
